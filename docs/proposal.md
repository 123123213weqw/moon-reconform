## 问题和使用对象

剪辑师重排、裁剪或复用镜头后，审阅人员在旧版记录的修改位置会失效。遇到同一素材多次出现时，直接套用原时间会把意见挂到错误的镜头。审片往往不止一轮：上一轮没处理完的意见，和已经写进工程的标记，都要能带到下一版。需要反复审片的小型制作团队可用本项目迁移单帧和区间意见，逐项确认多候选或无匹配的情况，并一轮一轮延续。

## 用法和实现

输入前后两版 `.otio` 工程与 JSON 审阅清单。命令 `plan` 将旧意见拆成唯一匹配、多候选、已删除和旧空白四类片段，附源素材帧和目标候选。审核者填入多候选片段的选择，`apply` 将完整解析的意见写为新工程轨道标记，并保留原有数据。缺失片段会使整条意见留待人工处理。

意见按素材认亲，不按时间码。留待处理的意见由报告的 `carry` 改写成锚定在源素材上的意见，直接粘进下一轮请求；请求置 `from_markers` 后，上一轮写入旧工程的标记自动读回成意见。`apply` 写出的标记记录自己落在哪段素材上，读回时只认这份记录，所以标记被剪辑软件按时间码搬动后，意见仍贴在原素材上；读回的意见迁移成功时，新工程里按时间码带入的旧副本同时被移除。

MoonBit 核心按素材索引新镜头，用整数半开区间和端点扫描定位重合范围，保留所有重复候选，不依赖逐帧遍历或视频解码。请求按名拒绝未知字段，写错的键不会被静默跳过。核心包不导入任何第三方包；交换层使用 MoonTimeline 已发布的 OTIO JSON 编解码器，无损保留数值与未知字段。跨版本审阅关联、候选决策、多轮延续和迁移记录由本项目实现。[上游 MoonTimeline](https://github.com/white-bear233/MoonTimeline)

## 复现与边界

仓库运行 `python scripts/verify.py --live-fixture`，由独立的逐帧预言机核对 40 对生成的剪辑和 480 条意见、160 条源素材锚点意见、留待处理意见的延续，以及一段三轮审片：5 个标记全部被按时间码搬动，18 条意见最终全部落在手算的位置。导出标记记录的素材由脚本自行枚举得出。11 个单元测试在 JS、Wasm、Wasm GC 和 Native 上运行，CI 对四个目标逐一检查。在固定版本的 ElFuente 60 fps 时间线上构造重剪，从 1430 帧改为 1036 帧，5 条意见迁移 3 条并保留 2 条待处理，导出的标记已用官方 OpenTimelineIO 0.18.1 读取核对。[ElFuente 验证素材](https://github.com/darbyjohnston/otio-oc-examples/blob/2cc61d92fb4c45dfc0ef8e80f4b5dd7c0005f25f/ElFuente_4096x2160_60fps_10bit_420.otio)

当前覆盖同整数帧率、单条视频轨道、可识别源素材 URL 的硬切工程，含重排、裁剪、素材重复和轨道空白。变速、转场、嵌套轨道和素材改名超出支持范围。素材重命名后无法再认出同一素材；剪辑软件若在导入导出时丢弃标记的 metadata，这些标记读回时会被当作剪辑师自己的标记跳过；0.2.0 之前导出的标记没有素材记录，读回时按名拒绝，需重新导出。
