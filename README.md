# MoonReConform

MoonReConform 将旧版剪辑上的审阅意见迁移到重剪后的 OpenTimelineIO 工程，画面轨道和声音轨道都可以。剪辑师可以追踪一段意见对应的素材帧，确认重复镜头的目标，或者把缺失素材和旧版空白上的意见留待人工处理。意见按素材而不是时间码认亲，所以能一轮一轮审下去：没处理完的自动带到下一版，已经写进工程的标记也能读回来接着用。

## 安装与运行

命令行使用 MoonBit 1.0（`1.0.0-rc1+3c0520448`）和 Node.js 22 或更新版本。仓库里的验证大部分只用到 MoonBit 工具链；命令行层面的复核脚本另需 Python 3.10 或更新版本，形式化证明另需 Why3。在仓库根目录运行以下命令。

```sh
moon update
python scripts/verify.py --demo _build/example
moon run cmd/main --target js -- plan _build/example/before.otio _build/example/after.otio _build/example/request.json
moon run cmd/main --target js -- apply _build/example/before.otio _build/example/after.otio _build/example/request.json _build/example/reviewed.otio
```

两条命令都在标准输出返回 JSON。失败时是 `{"ok": false, "error": "..."}` 并以非零状态退出，`error` 只写路径、用法或被违反的规则。`moon run cmd/main --target js -- --help` 打印用法。成功时其中 `notes[].pieces` 记录旧片段、源素材和所有新候选，`held` 记录待处理意见的 ID，`transfers` 记录可写入的片段，`carry` 把留待处理的意见改写成下一次请求可以直接使用的源素材意见。示例请求包含两项已确认的候选，最终写入五段标记，保留两条待处理意见。重新运行示例时给生成目录和目标 OTIO 选择新路径。更新内容见[更新日志](CHANGELOG.md)，依赖许可见[第三方依赖](THIRD_PARTY.md)。

## 审阅请求

```json
{
  "fps": 24,
  "old_track": 0,
  "new_track": 1,
  "notes": [
    {"id": "n1", "text": "检查对白入点", "start": 4},
    {"id": "n2", "text": "核对转场前的字幕", "start": 3, "stop": 6}
  ],
  "selections": [
    {"note_id": "n1", "piece": 0, "clip": 3}
  ]
}
```

- `old_track` 和 `new_track` 是各工程 `tracks.children` 中从零开始的索引，所选轨道可以是 Video 或 Audio。时间以所选轨道第一帧为 0，各端点为帧号。区间为 `[start, stop)`，省略 `stop` 表示单帧。
- 请求、单条意见和人工确认里的未知字段按名拒绝。例如把 `stop` 写成 `end` 会返回 `annotation n1: unknown field end`，不会把区间意见悄悄当作单帧意见。OTIO 工程自身的未知字段不受影响，原样保留。
- 从 `plan` 的报告确认 `ambiguous` 片段的候选，将选中的 `clip` 和该片段在 `pieces` 中的索引加入 `selections`，再用同一对 OTIO 文件执行 `apply`。新轨道中空白也占用子项索引。
- `unique` 表示恰有一个新位置，`ambiguous` 表示两个以上，`deleted` 表示没有新位置，`gap` 表示旧位置处于轨道空白，`offline` 表示片段没有可识别的素材（缺失、内嵌、由软件生成，或根本没有媒体引用），`transition` 表示转场，`nested` 表示嵌套进轨道的子序列。后四种片段没有素材帧，所在的意见留待处理，也不进入 `carry`。只有一条意见的全部片段解析完毕才会生成标记。有些意见会拆成数个标记，原 ID 和片段序号保存在 `metadata.moon_reconform`。
- 意见也可以锚定在源素材上：给出 `media`（素材 URL）和 `source`（素材帧区间），不给出 `start` 与 `stop`，例如 `{"id": "c1", "text": "核对片头", "media": "file:///shoot/A.mov", "source": {"start": 30, "stop": 33}}`。这类意见不依赖任何一版时间线上的位置，片段的 `old` 为 `null`。
- `carry` 为每条留待处理的意见列出其中有素材帧的片段，改写成上面这种源素材意见，ID 为 `<原 ID>#<片段序号>`，可以直接粘进下一次请求的 `notes`。旧版空白上的片段没有素材帧，不会进入 `carry`，仍需人工处理。
- `apply` 从输入重新计算，向新工程的选中轨道附加标记。保留现有标记及其余工程字段；没有任何意见迁移成功时不写入标记。目标目录需已存在且支持硬链接，目标文件需为新路径。输入有误、选择无效、标记键冲突或目标已有文件时，命令返回非零退出码。

## 反复审片

每一轮把上一轮 `apply` 的输出当作 `old.otio`。

1. 把上一轮报告的 `carry` 粘进这一轮请求的 `notes`。留待处理的意见在新时间线上没有位置，能带走的是它指向的素材。
2. 需要延续上一轮已写入的标记时，在请求里加上 `"from_markers": true`。旧工程选中轨道上带 `metadata.moon_reconform` 的标记按轨道顺序读回成意见，ID 为 `<原 ID>#<片段序号>`，排在手写意见之后，不必重新输入。读回的意见同样出现在 `carry` 里，没有处理完就继续带到下一轮。
3. `apply` 写入新工程时，读回的意见一旦迁移成功，剪辑软件按时间码带进新工程的那份旧副本会先被移除，再追加落在素材上的新标记。留待处理的读回意见不改动任何现有标记，旧副本留在剪辑师放置的位置。

`apply` 写出的每个标记在 `metadata.moon_reconform` 中记录 `note_id`、`piece`、`target_child`，以及它落在哪段素材上（`media` 和 `source`）。`from_markers` 读的是这份素材记录，不是标记此刻画在哪个时间码。剪辑软件按时间码搬动标记后，意见仍然贴在原素材上。报告的 `notes[]` 和 `transfers[]` 用 `origin` 指明一条意见读自哪个标记。ID 逐轮接续：`entire-old#0#0` 是意见 `entire-old#0` 的第 0 个片段。

读回时按名拒绝的情况：同一标记在旧轨道上出现两次（报出两处位置），`piece` 为负，素材记录缺失或区间为空，标记的 schema 不是 `Marker.1` 或 `Marker.2`。没有这段 metadata 的标记属于剪辑师，读回时跳过。标记的 metadata 能否随工程在剪辑软件中往返取决于所用软件；被丢弃的标记读回时等同剪辑师的标记，这时用 `carry` 和保存的请求 JSON 延续意见。0.2.0 之前导出的标记没有素材记录，读回时提示 `records no footage`，用本版本对当时的两个工程重新执行一次 `apply` 即可。读回的意见计入 10,000 条意见的上限，与手写意见 ID 重复时整份请求被拒绝。

## 支持边界

支持两版各选一条启用且未裁剪的 Video 或 Audio 轨道。轨道上的子项可以是 `Clip.1`、`Clip.2`、`Gap.1`、`Transition.1`，以及作为片段嵌入的 `Stack.1`。能按素材迁移的只有活动媒体引用为 `ExternalReference.1` 的片段：素材身份是 `target_url` 的逐字节完全匹配加帧区间，轨道种类不参与，URL 也不做 Unicode 规范化（`é` 的两种拼法算两种素材），所以同一段素材既可以在画面轨上，也可以在声音轨上。媒体缺失、内嵌、由软件生成或没有引用的片段报 `offline`；转场占 `in_offset + out_offset` 帧，报 `transition`；嵌套序列占其 `source_range` 的长度，报 `nested`。

两份工程和请求必须用同一个帧率，1–240，整数或 23.976、29.97 这类非整数都可以：库里的帧率用 `Rate` 表示，比较的是数值，24 与 24.0 是同一个帧率，29.97 与 29.97002997002997 是两个。帧号是帧率下的整数，可由 JSON 精确表示，最大为 `2^53−1`；不在帧率之间做任何换算，所以帧号在什么帧率下都保持精确。Premiere 等软件的导出会把片段的 `source_range` 写在素材自己的帧率上，例如 30 fps 序列里的一段 15 fps 素材，这样的轨道因帧率混杂被拒，报错写明两处帧率；不在 1–240 之内或不是正数的帧率也被拒。带效果或变速的子项、被禁用的子项、自身带 `source_range` 的轨道、其他 schema 的子项都被拒绝。所选轨道的 `markers` 里每一项都必须是对象，标记内部只有 `metadata.moon_reconform` 会被解读。

数字按原文写回。OpenTimelineIO 对非有限数并不严格，`Inf`、`-Inf`、`NaN` 可以读入，也照这个写法交还。写成有限数却超出 double 范围的数（如 `1e309`）读进来是无穷大，写回就成了 `Inf`，与原文不符，所以 `plan` 照常，`apply` 按原文拒绝。字符串按值保留，转义写法会规范化。CLI 读取 OTIO 和 JSON 文本，审阅意见由 JSON 请求提供。

核心将旧意见按镜头边界切分，再按新版本命中区间的端点扫描。素材 URL 索引先定位潜在镜头，再枚举实际覆盖片段的所有新位置，因此长区间无需逐帧扫描。单次分析最多接收每条轨道 20,000 个子项、10,000 条意见（含读回的标记）和 100,000 个人工确认。候选查找限额为 1,000,000 次区间检查，报告限额为 100,000 个片段及候选项，两个预算按单次分析计算。输入文件上限为 16,000,000 字节，所以这些限额相互制约：20,000 个子项加 10,000 条意见的最大请求里，最大的文件约 14.85 MB。

MoonTimeline 0.2.1 的 `otiojson` 负责读取与写回 OTIO 数值和未知字段。MoonReConform 提供跨工程的审阅范围映射、歧义确认和迁移报告。[MoonTimeline](https://github.com/white-bear233/MoonTimeline)

## MoonBit 库

在自己的项目执行 `moon add 123123213weqw/moon_reconform@0.7.0`，导入包 `123123213weqw/moon_reconform`。`read_otio` 和 `read_request` 读取两版时间线与请求，`plan` 返回逐段候选，`resolve` 应用人工确认，`carried` 给出下一轮的源素材意见，`read_notes_from_markers` 读回导出的标记，`with_markers` 返回附加了标记的新工程，`report_json` 输出与命令行相同的报告。帧率参数是 `Rate`：`Rate::whole(24)` 造一个整数帧率，非整数写 `{ value: 29.97, token: "29.97" }`。`Timeline::from_shots` 可接收程序自建的镜头，`Shot::Unplaceable(Offline | Transition | Nested, 长度)` 表示一段没有素材的时间。核心包不导入任何第三方包，只依赖本模块的 `123123213weqw/moon_reconform/spans` 和 `moonbitlang/core`，可在 JS、Wasm、Wasm GC 和 Native 构建。`spans` 是区间相交、搜索与排布的内核，它的契约经过形式化证明（见下文「形式化证明」），也可以单独导入。Node CLI 管理文件 I/O，并用 MoonTimeline 的 `otiojson` 无损读写 OTIO 文本。

## 验证

验证的主体是 MoonBit 自己的测试，在 JS、Wasm、Wasm GC 和 Native 四个目标上各跑一遍：JS 上 48 个，其余三个后端各 40 个。差的 8 个是命令行自己的规则，命令行只构建到 JS。Python 脚本留在进程层面：以进程的方式驱动编译好的命令行，检查文件读写、退出码，以及那些根本不是文档的输入。

```sh
moon check --target all --deny-warn
moon test --target native --deny-warn
moon run cmd/campaign --target native -- 200000 1 12
moon run cmd/campaign --target native -- mutate 200000 1
moon bench oracle --target native --release
moon prove spans
python scripts/prove.py
python scripts/verify.py --live-fixture --otio-samples
python scripts/fuzz.py --count 600
python scripts/mutate.py
```

**预言机**（`oracle/`）是一个独立的 MoonBit 包，用两种互不相同的算法算出每条意见的每个片段应当是什么。区间规划把每段素材与所有新位置做区间相交，在覆盖集合变化的地方切分，只用整数运算，任何量级都能算；逐帧枚举在剪辑足够短时把每一帧都查一遍。两者的结果都必须与报告逐项相等，`held`、`transfers` 和 `carry` 再由片段推出，报告与导出的工程也要与预言机写出的逐项相同。

生成器从一颗种子画出旧剪辑，再按剪辑师的方式重剪：丢段、重复、沿素材挪动一两帧、整轨轮转。子项有黑场、素材、脱机片段、转场和嵌套序列，边缘落在一张小网格上，所以片段边缘、意见边缘和重复素材经常重合。意见一半落在旧轨道上，一半锚定在新剪辑也有的素材上，因此迁移、留待和重复素材的歧义都常出现。之后还有第二轮：把上一轮写出的标记按时间码搬进第三版剪辑，读回、带上 `carry`，再迁移和导出一次。一颗种子在每个后端上是同一份审阅。

QuickCheck 属性共十一条：

- 生成的每一份审阅都如预言机所说（4,000 份，失败时收缩到最小的反例）。
- 剪辑与自身比对时，每条意见都落回原处（2,000 份）；素材挪到 `2^53 − 256` 附近再比一次（2,000 份），离开工具的每个帧号都贴近能写出的最后一个。
- 被变异器改过的审阅，要么被有理有据地拒绝，要么与预言机逐项一致（4,000 份，约 2,500 份答对、1,500 份被拒）。变异器做的事见下文「模糊测试」。
- 任意拼凑的 JSON，以及被换掉一部分的真实工程和请求，交给每一个读入口，都读入或被拒绝，绝不崩溃（3,000 份）。
- 帧号按十进制数字原样读入，或者被拒：3,000 个随机写法，判定用 `BigInt` 逐位做，另有一份边界清单，包括 `9007199254740991`、`9007199254740992`、`1e15`、`1e16` 和 `1.0000000000000001`。
- 证过的内核与逐个枚举的结果一致：前缀最大值、搜索的起点、两个区间的交、两数之和、首尾相接的排布（五条）。

另有七个规则测试钉住限额与预算的临界：候选查找预算在 999 条意见处接受、1000 条处拒绝；报告预算在 49 条处接受、50 条处拒绝；黑场上的片段也计入报告预算，五条意见占满、六条超出；10,000 条意见与 20,000 个子项读入，各多一个就被拒；100,001 个人工确认被拒；29.97 被告成帧率而不是坏数字，负数和一百万以上的小数才是坏数字；帧率 1 和 240 被接受，0 和 241 被拒；同一条意见不能往同一轨道上导出两次；轨道不列 `markers` 成员时，没有迁移就把工程原样交回。

**命令行自己的规则**。命令是一个带文件与输出的函数：终端把自己的读写交给它，测试交给它手头的。八个测试钉住这些：调用用错了就打印用法并失败，而且在读任何文件之前就停下；`--help` 和 `-h` 打印用法并成功；输入是至多 16,000,000 字节的常规 UTF-8 文件，正好这么多可读，多一字节不可读，不是 JSON 的把错处连同路径说出来；`plan` 打印核心的报告而什么都不写；`apply` 把带着标记的新工程写出来；写不出时把原因原样报告；`from_markers` 为真时旧工程里的标记被读回，接在手写的意见后面；核心的拒绝原样转述，不带源码位置。

**战役**（`cmd/campaign`）在一个进程里连跑几十万份审阅，不必每次启动 Node。Native 和 Wasm GC 各跑一百万份、JS 和 Wasm 各跑四十万份的一次战役里，一百万份覆盖 3,488,072 条意见、4,302,015 个片段，其中 962,607 次迁移、245,864 个片段有不止一个新位置；645,304 份带 `2^53 − 256` 附近的素材帧号，轨道位置超过 `2^31` 的有 645,846 份，约一半的审阅在 29.97 下。JS 与 Wasm 跑同样的四十万份时计数逐项相同，Native 与 Wasm GC 的一百万份也彼此相同，失败为零。换成变异模式（`mutate`）再跑一轮：一百万份里 645,263 份被工具接受并与预言机逐项一致，354,737 份被拒；JS 与 Wasm 的四十万份是 258,317 与 141,683。四个后端跑同样的份数时计数彼此相同，失败为零。这是在变异器找出预言机的一处不准并改过之后；改之前，一百万份里有 33 份对不上。

**形式化证明**。契约由 `moon prove` 交给 Why3 和三个 SMT 求解器（Alt-Ergo、Z3、CVC5）证明，两个包一起证：`spans` 八个目标，核心包四个。核心里能证明的是契约里不碰数组的那几处——`Span::length`、两数相加的边界、区间相交、时间线长度；数组上的事情由 `spans` 承担，因为 1.0 的前端在契约为 `.mbtp` 谓词取 `FixedArray` 参数时仍会与包内的 `Array` 类型相撞，`Array.length()` 也不能出现在契约里。`spans` 的八个目标是：

- `intersection`：两个半开区间的交是同时包含在两者之内的最大区间，非空，从其中一个的起点开始、在其中一个的终点结束；为空当且仅当一个区间在另一个开始之前结束。
- `first_above`：在只升不降的序列里找到第一个大于界的坐标。它之前的每个值都不超过界，它之后的每个值都大于界。
- `running_max`：每个位置都是起点值与此前所有值的最大值——至少是它们每一个，至多是任何不小于它们的东西，并且只升不降。
- `first_high`：搜索可以从哪里开始。它之前的每个值都不超过界，所以不会漏掉镜头；它又不晚于必须开始的地方。
- `summed`：两数之和恰在还能命名时给出；负数，或者超过 `2^53 − 1`，都得不到结果。
- `laid_out`：把一排长度首尾相接排开。每个停止位置是前一个加上自己的长度，第一个就是它自己，都是能命名的帧；放不下时就停在放不下的那个长度之前，并说明停在第几个。

两条引理把搜索的两端接上：在搜索起点之前结束的区间，与从起点开始的区间没有公共帧；只升不降的序列里，一旦某个值不早于终点，它之后的也都不早于，扫描可以在那里停。

没有证明的是逐片扫描本身、`resolve` 和 JSON 的读取，这些由预言机的属性覆盖。证明针对数学整数，不模拟 64 位回绕，上界由 `summed` 的契约和读取器的检查守住。`scripts/prove.py` 在证明之后把每条契约故意破坏十九处——搜索早一步停、前缀最大值滞后一位、交集可以为空、和可以越过最后一帧、排布从第一帧之外开始、停下了还接着排、引理的前提被抽掉——要求求解器逐处拒绝。仍然能证通过的破坏，就是一条没人写下来的规则。

**基准与覆盖**。`moon bench oracle --target native --release` 在一台 V100 工作站上：一份审阅走完工具和预言机，Native 0.60 ms、Wasm GC 0.47 ms、JS 0.80 ms；读入 20,000 个子项的工程 46 ms、76 ms、53 ms；1,000 条意见对 20,000 个子项规划 44 ms、34 ms、103 ms。`moon test --enable-coverage` 之后 `moon coverage report -f full_summary`：核心包 640/662，`spans` 36/36，命令行 43/53；JS、Wasm GC 与 Native 的数字相同，JS 另含命令行。

**Python 脚本**留在进程层面，并作为与 MoonBit 各写各的第二套实现。

- **复核脚本**（`scripts/verify.py`）以进程的方式运行编译好的命令行，也用 Python 独立算出每条意见的每个片段应当是什么，用的是同样的两种算法，与 MoonBit 预言机各写各的。它依次走过十段场景，另加两份来自网络的固定素材：
- 示例工程：5 条意见，2 条留待处理；含对未知字段、变速、非整数帧和无效选择的拒绝。
  - 40 组确定种子生成的剪辑和 480 条意见，同一批剪辑上的 160 条源素材锚点意见，以及留待处理意见的延续。
  - 三轮审片：第一轮写出的 5 个标记被按时间码搬进第三版剪辑后全部离开原素材，读回后 2 条落回素材，3 条随 `carry` 进入第三轮，最终 18 条意见全部落在手算的位置上。
  - 超出可枚举范围：素材起点在 `2^52` 量级、长 `2^51` 帧的剪辑、正好 `2^53−1` 帧的剪辑与自身比对，最后一个可表示的帧落在自己身上。`plan` 用时约 0.1 秒。
  - 命令自身的失败：20 组，逐条核对完整消息，包括正好 16,000,000 字节的输入可读而多一字节不可读，以及不可写的目录和不是目录的父路径。
  - 边角：12 组。空的剪辑；不说什么和说了五千字的留言；没有任何迁移时新工程原样写回；报告写到一半读端关闭管道；23.976、59.94、29.97 与 29.97002997002997 的帧率各走一遍迁移、导出与读回，两个相近的帧率被当作两个，不在范围内或不是正数的帧率被拒，帧号仍须是整数；脱机片段、转场和嵌套序列；按媒体 `available_range` 取长度的片段；逐字节匹配的 URL；25 个数字写法原样保留、`Inf`/`-Inf`/`NaN` 原样保留、溢出写法被拒；带引号、换行和控制字符的意见；读回的标记计入意见上限。
  - 音频轨道：画面与声音并排的两轨工程，意见落在声音轨上，第二轮读回时两份旧副本被取代、一份保留。
  - 预算与计数：候选查找预算在 999 条意见处接受、1000 条处拒绝，报告预算在 49 条处接受、50 条处拒绝；子项和意见在临界处被接受、越一步被拒绝；人工确认的上限受报告预算制约，只测越界拒绝；帧率 1 和 240 被接受，0 和 241 被拒绝；超出 Int32 或超出轨道栈的索引被拒绝。
  - 临界请求：20,000 个子项对 20,000 个子项、10,000 条意见，约 5 秒答完，每个落点经区间规划、逐帧枚举和闭式公式三方核对。
  - ElFuente：用固定提交和 SHA-256 的 60 fps 素材时间线生成一次重剪，1430 帧缩减到 1036 帧，5 条意见中迁移 3 条，保留 2 条。[固定版本的 ElFuente OTIO](https://github.com/darbyjohnston/otio-oc-examples/blob/2cc61d92fb4c45dfc0ef8e80f4b5dd7c0005f25f/ElFuente_4096x2160_60fps_10bit_420.otio)
  - OpenTimelineIO 项目自带的 13 个样例文件，固定到一个提交并逐个校验 SHA-256。42 条轨道里 23 条可读，包括一份 Premiere 导出里的 7 条、带转场的和没有媒体引用的；19 条被拒，原因是效果与变速、被禁用的子项、被裁剪的轨道、帧率混杂，每条拒绝的话都记录在案。可读的轨道同样三方比对，导出能用官方库读回（样例本身是为更新版本的库写的除外）。
- **模糊测试**（`scripts/fuzz.py`）以进程的方式把编译好的命令行再模糊一遍，变异与 MoonBit 里的是同一套主意：对示例的三个文档做一到三次变异——改帧号和索引（直到帧号能表示的边缘）、改 schema、轨道种类、素材 URL 和名称，删除、重复、移动或混入子项、标记、意见和确认，增删字段，按剪辑师的方式修改一个片段，或把一个值换成另一种类型。看的是进程层面的约定：每个变异都必须得到一个状态，退出码为 0 或 1，标准输出是一个 JSON 对象，标准错误为空；仍然是一对真实剪辑的，答案必须通过 Python 版的复核，能导出的再导出核对。另有 33 份根本不是文档的输入，包括空文件、单独的字节序标记、非法 UTF-8、`NaN`、20 万层嵌套、500 万字节的键。数字写法：随机生成帧号的 JSON 写法，用 Python 的精确十进制判定它该被接受还是拒绝。边界对齐的剪辑对：素材起点和长度取自一张小网格，片段边缘、意见边缘和重复素材经常重合，每个多候选片段用随机的合法确认来定，导出后再对着第三份剪辑按素材读回。CI 每次运行 600 个变异、400 个数字写法和 300 对剪辑；失败的尝试会把文档留在 `_build/fuzz` 下，按 seed 可以复现。

  在 0.4.0 上的一次战役里，两万个变异中 11,532 个被接受并逐个验证，179 个因数值过大只用区间规划验证，8,289 个被拒绝且各带理由；6,000 个数字写法里 1,698 个被接受且读回一字不差，其余被拒；20,000 对边界对齐的剪辑覆盖 79,887 条意见、1,492 次随机合法确认、4,693 次导出和 3,539 次第二轮读回。三件事都没有崩溃，也没有与复核不一致的。
- **故障注入**（`scripts/mutate.py`）保存 44 个已知故障，每个对应工具承诺的一条规则：片段冒称旧轨道上的范围、扫描晚一帧收尾、候选顺序、预算、限额、32 位截断、旧副本不被取代、标记按时间码读回、溢出数字照写、把 29.97 当成坏数字、转场只算一半、脱机片段报成黑场、命令行的各项规则等。每个故障在仓库的私有副本里注入、构建，`moon test` 或复核脚本至少有一个必须失败。44 个现在全部只凭 `moon test` 就能抓到：38 个在四个后端上都抓到，6 个命令行接线的——读入、写出、用法、帮助、输入上限和 `from_markers` 的调用——在 JS 上。复核脚本仍以进程的方式把它们再抓一遍，没有漏网的。
